I can see several candidates. Here's an analysis from most to least likely, based on what the code actually does:

1. WINHTTP_ACCESS_TYPE_DEFAULT_PROXY — highest likelihood
In http_client.cpp:19, every single request opens a new WinHTTP session with WINHTTP_ACCESS_TYPE_DEFAULT_PROXY. On Windows, this triggers WPAD (Web Proxy Auto-Discovery) — the OS checks the registry, then attempts a DHCP/DNS query for a PAC file before making the actual connection. If the network doesn't respond to WPAD probes, this can block for 5–15 seconds per session. It happens on every DoGet call because sessions are never reused.

Map loading kicks off equipment fetches, name lookups for every gear slot, trait/skill resolution — potentially dozens of WinHTTP sessions created in rapid succession, each paying the WPAD penalty. On Linux the WinHTTP call chain doesn't actually execute, so you'd never see this.

Fix: Change to WINHTTP_ACCESS_TYPE_NO_PROXY if you don't need proxy support, or create one persistent session at startup and reuse it.

2. Per-request session creation — amplifies #1
Each DoGet / GetPage creates a full WinHTTP session, connection, and request, then tears it all down. There's no connection pooling and no TLS session resumption. For the API host (api.guildwars2.com) every call pays the full TLS handshake (~100–200 ms on a warm network). Six sequential batch fetches in gw2names.cpp:306-310 each pay this cost, one after another inside the detached thread.

3. Detached threads + MinGW winpthread + DLL lifetime
At gw2names.cpp:358, the fetch thread is .detach()-ed. With MinGW's statically linked winpthread (your link flags on line 80 of CMakeLists.txt), winpthread's internal thread registry lives inside your DLL's address space.

When GW2 transitions maps, it may unload and reload addon DLLs. On unload, DLL_PROCESS_DETACH fires and winpthread tries to clean up its thread registry — but the detached thread is still alive, blocked inside WinHttpReceiveResponse. This is a known deadlock scenario specific to MinGW + statically linked winpthread in GW2 addon DLLs. It does not happen on Linux because you're not actually loading the DLL into a live process there.

Shutdown() at gw2names.cpp:361 only spin-waits if AddonUnload is called cleanly first. If the game unloads the DLL without that path, the thread is abandoned.

4. WinHttpOpen called from inside the loader lock window
During map transitions, the game's loader lock is held while loading/unloading DLLs. If anything in DLL_PROCESS_ATTACH (even indirectly through static initializers) calls WinHttpOpen, Windows' deadlock prevention kicks in and can stall. MinGW's static runtime initialization runs more global constructors than MSVC does, making this more likely to accidentally touch something that indirectly calls into WinHTTP or creates a thread.

What to investigate first

same change

Here's the sequence that could produce the null-deref in d3d11:

Map transition begins — Nexus calls AddonUnload(), which calls GW2Names::Shutdown()
Shutdown() spin-waits on s_fetching (line 363), so it blocks until the detached thread finishes
But: if something causes the DLL to be unloaded without going through AddonUnload() (e.g., a crash or forced teardown in another addon), DLL_PROCESS_DETACH fires while the thread is blocked inside WinHttpReceiveResponse
MinGW's statically linked winpthread tries to clean up its thread registry during DLL_PROCESS_DETACH, finds a live thread it can't join, and corrupts its own thread-local storage or heap metadata
This heap corruption doesn't crash immediately inside our DLL — it manifests later when GW2's D3D rendering allocates or accesses a structure that now has a nulled or corrupted pointer field
The Linux non-crash is explained simply: on Linux (Proton/Wine + DXVK), the D3D layer is completely different and more resilient to heap metadata corruption, and winpthread's behaviour in that environment is also different.

What to actually fix
The detach + winpthread combination is the real risk. The recommended change:

In gw2names.cpp, instead of detaching the thread and spin-waiting, keep a joinable handle:


// Replace s_fetching atomic + Shutdown() spin-wait with:
static std::thread s_fetch_thread;

// In FlushPending(), change:
std::thread([...]() { ... }).detach();
// to:
if (s_fetch_thread.joinable()) s_fetch_thread.join();

// In Shutdown():
if (s_fetch_thread.joinable()) s_fetch_thread.join();
This eliminates the detached thread entirely — winpthread's cleanup during DLL unload will find a properly tracked (and joined) thread rather than an abandoned one.

The project normally cross-compiles from Linux with the MinGW toolchain. On Windows the easiest path is MSYS2, which gives you the same MinGW-w64 compiler natively — no toolchain file needed.

One-time setup
Download and install MSYS2 from msys2.org
Open the "MSYS2 MinGW x64" shell (not MSYS2 MSYS or UCRT64)
Install the toolchain:

pacman -S mingw-w64-x86_64-cmake mingw-w64-x86_64-gcc mingw-w64-x86_64-ninja
Building
From the MSYS2 MinGW x64 shell:


cd /c/Users/s-r-b/OneDrive/Documents/GitHub/gw2-build-coach

cmake -S . -B build -G "Ninja" -DCMAKE_BUILD_TYPE=Release

cmake --build build --parallel
The output is build/BuildCoach.dll.

Do not pass -DCMAKE_TOOLCHAIN_FILE=mingw-toolchain.cmake — that file is for cross-compiling from Linux. On Windows with MSYS2 MinGW you're already using the right compiler.

Install directly to GW2 addons folder

GW2_ADDONS_DIR="C:/Program Files/Guild Wars 2/addons" cmake --install build
Or just copy build/BuildCoach.dll manually to C:\Program Files\Guild Wars 2\addons\BuildCoach\.
